# STE Assistant 0.3.3 — зависание экспорта

В STE 7.10 `GCodeWriter.write()` вызывает `_createSnapshot()`, помеченный
`call_on_qt_thread`. Этот декоратор всегда ставит callback через `callLater`
и ждёт `finish_event` без проверки текущего потока. Раньше ToolRegistry
запускал весь writer внутри MainThreadBridge.invoke: главный поток ждал
callback, который мог выполнить только он сам. Таймаут моста не снимал блокировку.
У ThreeMFWorkspaceWriter аналогичным декоратором помечен весь `write()`.

Теперь общий путь ToolRegistry для export_gcode/save_project, включая
compare_variants, вызывает SlicerAdapter.export_file из рабочего потока.
Получение writer, проверка завершённой нарезки, снимки сцены/настроек и
проверка результата выполняются через мост в Qt. Штатный writer выполняется
в рабочем потоке, как в нативном UM.FileHandler.WriteFileJob; его собственные
запросы миниатюры/3MF обрабатываются свободным главным потоком.
Запуск export_file из потока владельца моста явно отклоняется.

Сохраняются временный файл, проверка пути, положительный результат writer,
непустой файл и атомарная замена. Перед публикацией дополнительно проверяются
отмена, сцена, настройки, поколение нарезки и актуальность G-code. Изменившийся
или отменённый результат удаляется и не получает ссылку на скачивание.

Проверки: tests/test_exports.py проверяет оба writer с синхронным обращением
к главному потоку, ссылки скачивания, отмену, ошибки writer, изменения
сцены/настроек/G-code и новую нарезку. tools/host_export_regression.py
запускает установленный GCodeWriter и настоящий call_on_qt_thread в Python 3.5
STE: callback миниатюры исполняется, заголовки и G-code записываются.
В этой изолированной проверке отрисовка OpenGL и метаданные заменены фикстурами;
пользовательский проект не меняется. Полный GUI-экспорт нужно повторить после
перезапуска STE, чтобы он загрузил обновлённый плагин.
